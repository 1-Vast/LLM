**我的建议是：保留“双核心”，把系统收敛成一条决策主路径和一条结果回流路径。优化重点应是减少重复决策、统一状态与预测语义，并让真实结果能够持续修正后续选择。**

检查最新提交 `83ccd6e1` 后，我的判断是：框架已经具备不少必要能力，当前主要问题是**同一科学过程分散在多个接口、选择器和状态记录中，导致两个核心的作用难以追踪和归因**。继续增加模块会放大这一问题。

本轮没有修改源码；除了静态审查，还用一个内存案例复现了下文的校准标签问题。

**几个最值得优先处理的问题，已经能够定位到具体代码。**

| 现状 | 对双核心联动的影响 | 建议 |
|---|---|---|
| `orchestrator.py` 约 2,314 行，同时负责规划、预测调度、选择、修复、结果接纳、评分和日志 | 很难判断最终行动由谁决定，局部修改容易改变其他路径 | 保留一个编排入口，把计算和状态更新交还已有组件 |
| `run()` 中先规划，再预测、评审、重新选择、修复，之后还会过滤执行动作 | 多处都能改变计划，前面的评审可能针对已被替换的计划 | 每轮只允许一个位置提交最终计划 |
| `StatePrediction` 与 `OutcomeForecast` 分属两条预测路径 | RNA 响应、实验读数和机制判别之间缺少统一的任务描述 | 统一查询与返回外层，保留不同预测目标的类型区别 |
| 默认 expected-coverage 路径不使用预测幅度；outcome forecaster 默认不注入 | 系统运行了虚拟细胞，不代表它影响了选择 | 显式记录预测的用途，并配置可审查的决策策略 |
| 预测—结果匹配与可靠性记录默认保存在内存 | 重启后无法完整延续模型反馈 | 持久化预测、执行与结果的关联 |
| CaseStore、EpisodeStore、EvidenceState 等分别维护科学过程的一部分 | 容易出现重复事实、状态不同步和多套接纳逻辑 | 每类事实只设一个权威写入口，其余作为派生视图 |

这里不应把“预测幅度没有直接进入默认选择”简单当成缺陷。代码明确记录了此前幅度优先策略的负结果，保守默认有依据。需要修复的是**联动方式和可归因性**，而不是直接打开某个开关，让 STATE 获得更大权重。

**两个核心应共享同一个实验问题，但分别承担明确职责。**

智能体负责：

- 根据目标、证据和约束，构造可执行的候选干预与测量；
- 明确需要预测什么、什么结果会改变当前选择；
- 根据预测和真实证据决定行动、补证或停止。

虚拟细胞负责：

- 对给定状态和干预预测受支持的结局；
- 给出动作间差异、适用范围和不确定性；
- 接受后续真实结果的评分，形成有范围限制的可靠性记录。

两者通过同一个案例状态协作：

```mermaid
flowchart TD
    R["持久化实验记录"] --> A["智能体：问题、计划与选择"]
    R --> V["虚拟细胞：响应与不确定性"]
    A -->|"状态、候选动作、预测目标"| V
    V -->|"预测、动作差值、适用范围"| A
    A -->|"提交最终计划"| X["实验执行接口"]
    X -->|"真实结果"| E["统一结果接纳"]
    E -->|"更新证据与计划状态"| A
    E -->|"匹配预测并评分"| V
    E --> R
```

图中的执行、接纳和记录可以由现有代码承担，不需要再创建一个独立“总控智能体”或第三套认知核心。

双核心也不意味着每轮必须调用两个大模型。模型不适用、没有新信息或当前动作已确定时，跳过无价值调用是正确行为。

**我会先整理决策权，而不是先拆文件。**

当前 orchestrator.py[orchestrator.py](sandbox:/workspace/scratch/6e9a57b54dd1/repo/src/agent/orchestrator.py) 的问题并不只是长，而是承担了多次计划变换。

建议把一轮执行收敛为以下顺序：

1. **恢复当前案例状态。** 如果仍在等待结果，直接返回等待状态。
2. **智能体提出候选及预测问题。** 此时是候选，不是已经提交的执行计划。
3. **检查前提、预算与模型支持，查询必要预测。**
4. **一个决策入口评估候选并形成最终计划。** 修复失败就返回明确缺口；修复改变了预测问题，才重新查询受影响部分。
5. **冻结并提交计划。** 执行接口只接受该版本。
6. **真实结果到达后，通过统一入口接纳、评分和更新。**

其中有两个可以直接减少复杂度和成本的修改。

一个是把等待状态检查前移。当前代码虽然会阻止等待期间提交新执行动作，但此前已经进行了任务解释、规划、预测和评审。这些调用大多没有必要。

另一个是把便宜的检查放在推理之前。当前虚拟细胞查询早于预算选择，可能对本轮不会执行的动作也做完整推理。应先确定哪些候选当前可执行，哪些需要补前提，再按当前决策需要查询。暂时缺前提的动作可以保留在候选空间中，不必全部提前模拟。

文件层面，可以将：

- `_predict_many()`、预测缓存与后端调度归入已有虚拟细胞运行层；
- `_score_prediction()` 的评分计算归入已有校准代码；
- 结果接纳与证据变化归入 `maestro.outcome`；
- 选择计算集中到 `maestro.acquisition`；
- `orchestrator` 只负责顺序、依赖注入和失败处理。

**不要将大文件机械拆成十几个互相调用的小类。** 判断是否拆分，应看它是否拥有独立的输入、输出和职责，而不是行数。

**预测接口最需要统一的是“科学问题”，不是把所有结果塞进一种数据结构。**

目前 interface.py[interface.py](sandbox:/workspace/scratch/6e9a57b54dd1/repo/src/virtual_cell/interface.py) 的请求绑定了具体 `model_version`，`SystemContext` 主要携带数据集和背景信息；另一边 `UserStateContext` 又维护方向性状态和历史信息。

建议分清两层：

| 层次 | 应描述的内容 |
|---|---|
| 科学查询 | 当前状态、动作、时间、终点、条件化对象、预测人群 |
| 执行绑定 | 使用哪个 checkpoint、输入转换版本、抽样设置、运行环境 |

智能体提出科学查询，后端适配器负责将它绑定到具体模型。实际运行仍必须固定模型和输入身份，不能因此放松可复现要求。

这样可以消除两个问题：

- 智能体不需要知道 STATE 的具体数据标签和 checkpoint 细节；
- 更换后端时，能够确认比较的是同一个科学问题。

状态本身也应成为明确输入。建议复用现有资产引用机制，让请求指向一个不可变的状态记录，至少包含：

- 状态数据及内容摘要；
- 特征轴与预处理版本；
- 对应实验单位；
- 采集及可用时间；
- 作为当前状态还是历史观测使用。

不需要立即创建新的状态管理平台，关键是避免仅用 `dataset_id` 代表实际输入状态，也避免从自然语言描述中猜测状态身份。

返回值可以统一外层身份、支持范围和失败原因，但内部必须区分：

- 连续 RNA 或表型预测；
- 成功测量条件下的读数分布；
- 包含 QC 失败等情况的完整实验结局分布。

**“成功测量后的读数概率”不能通过接口转换就变成“整个实验的成功概率”。** 缺少这部分信息时，框架应保留限定预测，并让相应决策计算明确不可用。

**虚拟细胞应提供可比较的预测，智能体负责把它们映射到目标。**

目前 `_prediction_action_priorities()` 使用的是：

\[
\text{priority}(a)
=
|\widehat y_a|
\times\text{relevance}(a)
\times\text{reliability}(a).
\]

代码对这个量的用途做了限制，但它仍然只是幅度启发式。它没有表达：

- 指标应该升高还是降低；
- 是否接近目标状态；
- 是否违反约束；
- 动作之间的优势有多大；
- 新测量是否会改变后续决定。

建议逐步退出“响应幅度作为通用动作优先级”的设计，在现有决策层中显式定义目标。

例如，响应优化任务使用：

\[
\widehat U(s,a)
=
\mathbb E[u(Y,a)\mid s],
\]

机制补证任务则使用：

\[
\text{测量价值}
=
\text{预期决策损失下降}
-
\text{测量成本}.
\]

这两种任务可以共享执行框架，但不应该共享一个含义模糊的总分。预测任务不必因为没有完整成本而停止；需要计算净决策价值时，才要求相应成本和结局支持。

对于上一轮讨论的状态信息问题，建议在现有预测接口增加**同一比较组的批量查询能力**：

- 同一个基线状态；
- 同一组抽样索引；
- 多个候选动作；
- 同一个终点定义。

这样才能直接估计：

\[
\widehat D_{ab}(s)=\widehat U(s,a)-\widehat U(s,b)
\]

以及配对误差，而不是把几个独立请求的边际预测事后相减。

这可以作为现有接口的一个批量入口，不需要另外创建“状态交互智能体”。如果后端的计算依赖 batch 内细胞关系，还必须验证批量组织方式没有改变模型语义。

**真实结果回流是最应优先加强的联动部分。**

orchestrator.py[orchestrator.py](sandbox:/workspace/scratch/6e9a57b54dd1/repo/src/agent/orchestrator.py) 已经实现预测评分，而且允许合格但不能判别机制的观察参与评分，这是正确方向。实际缺口在于预测匹配和可靠性记录默认不持久化。

建议沿用现有 SQLite 基础，将下面的关联保存下来：

\[
\text{案例版本}
\rightarrow
\text{计划动作}
\rightarrow
\text{执行尝试}
\rightarrow
\text{预测记录}
\rightarrow
\text{真实结果}.
\]

尤其不要只靠 `action_identifier` 匹配预测。同名动作可能在不同案例、不同轮次被重复执行；没有案例信息时，匹配到“最近一次同名动作”存在歧义，应要求补足执行身份。

现有几种存储可以保留，但职责应收敛：

| 现有结构 | 建议保留的职责 |
|---|---|
| `CaseStore` | 计划、执行、结果与版本的权威记录 |
| `EvidenceState` | 从已接纳证据派生的当前假设与前提状态 |
| `EpisodeStore` | 从案例记录生成的科学案例视图，供检索和研究使用 |
| `MemoryStore` | 工作摘要与叙述性记忆，不拥有实验事实写权限 |
| 可靠性 ledger | 从预测—结果配对生成的评分与适用范围视图 |

这比强行把所有数据库合成一个大对象更稳妥。**统一的是事实来源和写入口，读取方式可以不同。**

此外，case_update.py[case_update.py](sandbox:/workspace/scratch/6e9a57b54dd1/repo/src/maestro/case_update.py) 中有一处应先修正的具体语义问题。

我复现的输入是：

- 预测 `unresolved` 的概率为 0.8；
- 实际读数也是 `unresolved`；
- QC 通过，但没有淘汰任何假设。

代码写出的记录却是：

| 字段 | 当前记录 |
|---|---|
| `kind` | `reading_probability` |
| `forecast` | 0.8 |
| `realised` | 0.0 |

原因是目标值由“是否达到 `OutcomeQualification.QUALIFIED`”决定，而该状态还要求发生假设淘汰。

这混淆了：

1. 读数预测是否正确；
2. 测量是否合格；
3. 测量是否足以判别机制。

正确做法是保存完整类别分布及真实类别，用 log loss 或 Brier score 评价读数预测；QC 与机制判别分别记录。这个复现确认了该函数的记录语义问题，不能据此推断所有历史实验都受到了影响。

回流也不必立即在线更新大模型参数。现阶段更稳妥的是：

- 实时更新证据、配对评分和适用范围；
- 在独立开发数据上拟合收缩或校准参数；
- 通过验证后发布新的模型或校准版本。

这样既有学习闭环，也不会把评价数据悄悄变成训练数据。

**知识、记忆和 Jev 应服务于这条主路径，避免形成各自的决策系统。**

当前知识相关结构分布在 `agent.knowledge`、`problem_compiler`、`virtual_cell.biology` 和 `pharmacology`。这些内容不必全部合并，因为它们分别涉及来源、问题表示、观测映射和药理计算。

更重要的是规定知识进入系统后的用途：

- 改变候选动作或必要前提；
- 改变有来源支持的预测输入；
- 说明哪项测量能够区分竞争解释。

如果一条知识只增加了提示词长度，没有改变其中任何一项，就不应进入每轮主上下文。

`HypothesisGraph` 可以保留为问题表示和解释工具，不必继续扩展成一个并行推理引擎。一个假设路径若无法映射到可查询预测或可执行测量，应标为尚不可操作，而不是靠增加关系节点补齐。

Jev 也应保持可插拔：

- 确定性的条件、预算和身份检查由代码完成；
- 只有语义歧义、解释冲突或计划修复确实需要时，才调用模型评审；
- 评审针对准备提交的计划，并返回建议；
- 它不成为另一处最终行动选择入口。

同样，任务解释无需每轮从原始用户消息重新生成。目标和约束没有变化时，应复用已确认的结构化任务，只让新证据驱动计划调整。

**智能体的价值应体现在提出更好的实验问题、利用反馈改变计划，而不以调用次数体现。**

**计算优化应围绕同一科学输入的复用开展。**

state_adapter.py[state_adapter.py](sandbox:/workspace/scratch/6e9a57b54dd1/repo/src/virtual_cell/state_adapter.py) 当前通过子进程调用 `state tx infer`。这是清晰的隔离边界，但多动作比较会反复启动推理进程。

在输入语义确定以后，可以考虑：

- 同一 checkpoint 在一个本地 worker 中只加载一次；
- 同一状态资产读取、转换一次；
- 同一比较组复用基线抽样；
- 相同查询继续使用已有缓存；
- 超时和失败仍由适配器返回明确结果。

不必为此建设分布式推理服务。先证明一个常驻 worker 能保持数值行为和隔离性，再考虑并行。

缓存也应分清两种内容：

- **原始预测缓存**：由模型、状态内容、动作、预处理和抽样设置决定；
- **决策派生结果**：还依赖目标、校准版本与当前证据。

目标或可靠性变化时，旧的原始预测可能仍然可用，但旧的动作评分不一定可用。

**判断重构是否成功，需要验证联动，而不仅是测试数量。**

工程验收应集中在几个高价值场景：

- 同一案例重启后，原预测仍能与迟到的结果正确配对；
- 同一结果重复导入，不重复计费、更新证据或评分；
- 两个案例使用同名动作，不交叉匹配；
- 等待结果期间，不触发新的规划和推理；
- 状态或动作改变，只使相关预测失效；
- 模型不可用时，智能体仍能给出合法的补证或停止方案；
- 没有新证据时，不因重启恢复已被排除的解释。

科学验收则需要一个双方都能发挥作用的比较，而不是简单“有模型/没模型”：

| 策略 | 上下文均值预测 | 状态条件化预测 |
|---|---|---|
| 固定的一步选择器 | \(V_{00}\) | \(V_{01}\) |
| 使用反馈调整计划的智能体 | \(V_{10}\) | \(V_{11}\) |

这里的一步选择器也必须能消费预测，否则第一行会天然不受世界模型影响，无法识别交互。

可以检查：

\[
\Gamma
=
V_{11}-V_{10}-V_{01}+V_{00}.
\]

正的 \(\Gamma\) 支持额外的联动收益，但不应人为要求它一定为正。实际标准仍是完整系统是否超过最强简单方案，以及改善是否来自状态预测和反馈利用。比较必须使用相同候选、真实测量预算、终点与数据边界；不支持某个预测目标的后端不能靠填默认值加入实验。

**实施上，我会按三个阶段推进：**

1. **修正反馈语义并补齐持久化。** 修复校准标签，保存预测—执行—结果关联，前移等待检查。
2. **收敛运行路径。** 一个最终计划提交点、一套科学查询接口、一条结果接纳路径；先保持既有策略行为，验证迁移等价。
3. **增强有证据支持的联动。** 加入配对动作比较、目标明确的选择计算，再通过真实数据比较决定是否提升为默认策略。

每增加一项能力，都应回答：**它替代了哪段重复逻辑，或者让哪项原本无法验证的双核心作用变得可验证？** 如果两者都没有，就暂时不进入主框架。
