# Dual-core repair: executable feedback and archive search

This is an engineering repair and exposed-data development replay. It does not
replace, reopen, or reverse the frozen study in the adjacent original folder.
All final labels were previously exposed. No result here is independent
confirmation, laboratory efficacy, open-ended evolution, or a demonstrated
innovation. The original negative deployment decision remains in force.

## Fixed scope before execution

1. Seed Python, NumPy and torch before constructing PPODE. Reuse the original
   width-16 architecture, masked loss, and 30 training epochs. Train only on the
   original five development lineages; select programs on the original five
   selection lineages. The original seven final lineages are used only for a
   post-selection regression replay. This is a different training allocation
   from the original final model and must not be treated as a paired model gain.
2. Keep scoring, outcome lookup, query costs and model updates in the parent
   process. Candidate code receives public JSON and returns one action per call.
   It cannot return authoritative scores. Reject malformed, duplicate,
   over-budget and unavailable actions. Any worker or program failure invalidates
   the episode, rather than becoming a zero score in search or evidence.
3. A functional query costs 1; a 24-hour molecular query costs 0.5; total budget
   is 5. These are hypothetical relative costs, not measured assay costs.
   Measured molecular values and functional labels enter a copied PPODE only
   after the parent validates and pays for the action. Update all model
   parameters for two AdamW steps at learning rate 0.0005 on accumulated support.
   Use only the 24-hour molecular mask. Record before/after parameter hashes and
   changes in remaining-drug predictions. A parameter change is not a benefit.
4. Compare fixed B1 confirmation, conventional B1 kernel feedback, frozen PPODE,
   updating PPODE, and a molecular-first updating PPODE procedure. The task is
   confirmed positive single-drug labels; pair labels remain unauthenticated.
   Separate transfer checks exclude every revealed support drug from evaluation.
5. Run three inherited and three restart API proposals, at most six logical
   requests and six HTTP attempts, at most 24,000 provider tokens (conservative
   input/output reservations before calls), 1,500 output tokens per request,
   temperature 0.7. Save full public prompts/responses and usage without secrets.
   Use distinct generation objectives, the actual selected parent, and previous
   evaluation evidence. A failed/duplicate proposal is reported; it cannot be
   silently treated as a novel evaluated candidate. Each arm has three candidate
   evaluation slots on the same selection episodes. Source duplicates consume
   no new evaluation slot; a predeclared conventional fallback fills that slot
   and is explicitly attributed to the fallback, never the LLM. Arm summaries
   distinguish budgets, actual computation, code diversity and API usage.
6. Inspired by DGM, retain valid behaviorally distinct non-winning programs as
   exploration parents. Program ancestry and restart roots are explicit.
   Deployment requires strictly positive mean selection gain over incumbent;
   this is development selection, not a significance gate. A separate old-final
   regression evaluates the deployed programs without further selection.
7. Freeze source/settings/program choices before old-final regression. Do not
   optimize on its outputs. Summarize paired differences and descriptive lineage
   bootstrap intervals, preserving duplicate clusters. No threshold adjustment
   can turn these exposed observations into scientific confirmation.

## Verification and stopping

Require adversarial runner tests, seeded initialization/training tests,
support-only update tests, archive non-winner-parent tests, persistence and
invalid-evidence tests. Run the complete real-data training, selection, bounded
API, program freeze and regression workflow. Recompute trace scores and budgets,
check episode coverage, resource counters and frozen hashes without retraining.
Compare all 222 original non-bytecode file hashes against the pre-repair snapshot.
Run the original verifier, original 11 tests, and the maintained repository suite.

No unrestricted generated code is permitted. The restricted Python worker is a
defense-in-depth mechanism, not an OS filesystem/network sandbox; arbitrary DGM
repository edits would require a separately isolated execution environment.
Failure of a research comparison remains a negative result even if every software
test passes. Stop expanding this configuration if practical advantage is absent.
