## Code-to-claim scope

The code reads both XLSX archives as ZIP; resolves workbook relationships to every worksheet; parses **entire** sharedStrings.xml into a Python list, and every selected worksheet XML into an ElementTree. Thus it transiently materializes full worksheet bytes/strings, including beyond row2, inside its extraction process. It also retrieves raw `<v>` text for top-row cells before checking cell type, so numeric literal text may transiently exist even though never converted to phenotype numbers or exported. A claim of no numerical bytes parsed, no numerical text internally accessed, or strict untouched-label physical isolation would be false. HEADER_PROTOCOL already explicitly permits underlying byte materialization and calls this logical text export restriction; keep that caveat.

Export loop checks row.r<=2, skips cells with a formula element, then exports only shared-string or inline-string cell types. Other typed/numeric/boolean/error `<v>` values are not exported. Shared-string index int conversion is an address lookup, not a response conversion. Existing JSON declares worksheet_numeric_values_exported=false, formula_text_exported=false, rows_text_exported=[1,2] and binds the protocol checksum. Those statements are consistent with static code inspection. A value stored as textual digits would still pass the type rule and is not semantically guaranteed nonnumeric; inspected output is mainly schemas, IDs, table descriptions and dates/count labels, not observed phenotype scalar cells. Static review does not independently prove original execution order or rule out information seen in previous unlogged activity.
