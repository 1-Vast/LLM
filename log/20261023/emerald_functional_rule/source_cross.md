## Parquet access guarantee must be accurately named

Arrow parquet row filtering is not a cryptographic or physical isolation barrier. With the actual single-row-group file, a scanner filtering dev contexts and allowed conditions may decompress/decode the growth column containing reserved rows before row selection. A subprocess itself does not change this decoder behavior. Therefore do **not** claim reserved numerical values were never physically decoded or never transiently materialized inside the projection worker.

Recommended minimum guard: a standalone projection subprocess with frozen small code, allowed context/condition identities fixed before execution, exact column projection/filter, no row/value console output, and only dev-whitelist rows written to a separate artifact. Validate output identities against the whitelist before fitting; no reserved IDs, no forbidden condition, no unrestricted summary stats; checksum source/whitelist/export. Modeling/selection process reads only that export, not original parquet; reserve values are not exported, retained in scientific artifacts, inspected, used for fitting, or used for selection. Document that the low-level decoder may handle reserved values transiently in the same row group. This is honest **logical export/access isolation**, not literal non-decoding.

If literal nonmaterialization is a requirement, it needs independently supplied row-group/partition-isolated input upstream; this local parquet cannot provide that guarantee through row filtering. That stronger barrier is unnecessary for an explicitly retrospective logical-holdout benchmark if accurately disclosed. Do not postpone the bounded screen for impossible local claims, and do not silently weaken a freeze that promised literal nondecoding: correct the protocol before opening.
